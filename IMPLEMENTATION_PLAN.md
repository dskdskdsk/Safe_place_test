## 3. Погоджена модель: факти, контекст, достатність даних

Усі обчислення локальні. Текст і голос не аналізуються за змістом. Не створювати загальний індекс, який змішує оцінки, емоції та кількість записів довільними вагами.

Один запис і оцінка 8 означають високу зафіксовану оцінку. Це не доводить спокій чи рівність дня. Кількість записів характеризує ведення щоденника, не якість дня й не статистичну незалежність спостережень.

### День

Валідна оцінка: числове скінченне значення 1–10; підтримати числа та об'єкти {v,t,...}. Не перетворювати рядки на числа непомітно. Зберегти чинне сумісне читання: валідні dayRatings; якщо таких немає — валідний legacy dayRating. В аналітиці відсутній результат — null, не 0.

- D = Σr / n — середня дня. Кожен оцінений день має однакову вагу у періоді.
- R = max(r) − min(r), якщо n≥2, інакше null.
- V = Σ|r−D| / n, якщо n≥2, інакше null.
- Кількість відправлених записів J: непорожні текстові та голосові записи з audioId; summary не дублює summaryEntries. Старий суцільний summary — один legacy-запис, лише якщо немає придатних entries та немає _summaryCleared.
- Емоції: множина валідних ID із емоцій дня й записів, без повторного підрахунку. Урахувати legacy emotion/emotionId без мутації.
- Статус: стандартний/власний ID, відсутність — unknown. Нерозпізнаний збережений ID не губити; показувати як невідомий контекст.
- Звички: тільки habitLog через чинний ключ habitId+'_'+dateKey. day.habits не використовувати як альтернативне джерело.
- Дні з кількома оцінками не стають «точнішими» автоматично. Розмах також залежить від числа спостережень; n завжди доступне в деталях.

### Період

Підсумок завжди стосується вибраних календарних дат. Майбутні дні виключити. Календарні дати перебирати як локальні дні, а не кроками по 86400000 мс. Тиждень починається в понеділок.

- M = ΣD/N, N — число оцінених днів; також медіана D.
- Покриття оцінками/емоціями/статусами/записами рахувати окремо від числа минулих календарних днів.
- Окремо: записи без оцінок, оцінки без записів, дні без зафіксованих даних.
- B = median(|D−median(D)|) — міжденний розкид. Для одного дня не описувати стабільність періоду.
- A = mean(|Dдень−Dпопередній|) — лише пари сусідніх календарних днів з оцінками; показувати число пар, за відсутності пар null.
- Ритм записів: загальна кількість, дні із записами, медіана J серед днів із записами.
- Частота емоції = дні з емоцією / дні з будь-якими емоціями. Сума часток може перевищувати 100%, оскільки вибір множинний.
- Поєднання позитивних і негативних емоцій — факт співіснування, не діагноз нестабільності. Невідома категорія не стає нейтральною.
- Річне середнє — середнє днів, не невиважене середнє місяців.
- Перший збережений змістовний день не вважати доведеною датою початку користування. Покриття рахувати за явним календарним діапазоном; доступний початок історії показувати окремо.

### Час

Старе HH:MM не доводить час спостереження: оцінки можуть бути внесені заднім числом. Старі оцінки залишаються придатними для середніх і розкиду. Для нового алгоритму не будувати часові висновки з unknown-походження.

Нова мітка підтверджує час внесення, а не час пережитої емоції. Майбутня часова аналітика використовує лише дані з відомим походженням, внесені в дату оцінюваного дня, без редагування; інтервал 60 хвилин — додатковий продуктовий фільтр. Формулювання: «між зафіксованими оцінками». Етап A лише готує дані; поведінку чинних стрілок графіка не розширювати в цьому етапі.

## 4. Зв'язки та правила показу для Етапів B–D

### Часові вікна

- Тиждень/місяць: описовий підсумок за вибраний період. Історичні зв'язки — за 84 календарні дні включно до останнього минулого дня цього періоду. Показувати фактичні дати.
- Рік: вибраний календарний рік до поточної дати. Перевіряти повторюваність за тижнями всередині нього.
- Історію не брати після кінця вибраного періоду. Часткові крайні тижні використовують лише дні всередині вікна, без добору днів зовні; позначати їх у деталях.
- Порівняння періодів: однакові минулі календарні відрізки. Поточний тиждень до п'ятниці — з пн–пт попереднього. Місяць — однакові номери днів у спільному діапазоні; рік — відповідні місяць/день, 29 лютого без пари виключити з обох порівнюваних наборів. Дати й n показувати.
- Особистий базовий рівень: вісім завершених тижнів перед початком вибраного періоду, мінімум 20 оцінених днів у чотирьох різних тижнях. Це окреме вікно від 84 днів для зв'язків.

### Групи

Звичка A: є відмітка; B: відмітки немає, але є інші відправлені дані дня. B не називати невиконанням. Чисті чернетки та автоматично створені порожні days не утворюють B. Статус, емоція, оцінка, відправлений запис, збережена подія/ідея/вдячність/медіа або інша відмітка звички — спостережувані дані дня.

Немає надійної історії створення/видалення/зміни звичок. Для звички обмежити доступні порівняння від першої наявної відмітки, пояснюючи цю межу. Видалену історію не відновлювати здогадками. Ціль 1–7 разів на тиждень не доводить фактичне виконання.

Статус A: вибраний ID; B: інші відомі статуси. Unknown не включати до B. Емоція A: вибраний ID; B: є інші емоції, але немає цього ID. Дні без емоцій не включати до B.

Для середніх використовувати лише оцінені дні груп. Для покриття групи — усі спостережувані дні, які можна до неї віднести. Показувати покриття окремо для A і B; не заповнювати пропущені оцінки.

### Різниця й повторюваність

Δ = mean(D_A) − mean(D_B).
Придатний тиждень має nA≥1 та nB≥1 оцінених днів.
Δ_t = mean(D_A,t) − mean(D_B,t).
w_t = nA_t*nB_t/(nA_t+nB_t).
Δ_local = Σ(w_t*Δ_t)/Σw_t.

Три рівні:
1. Факт: описові числа з доступних даних, без групової різниці, якщо одна група порожня.
2. Порівняння: щонайменше 5 оцінених днів у кожній групі.
3. Повторюване спостереження: N_A≥10, N_B≥10, K≥6 придатних тижнів; однаковий ненульовий знак Δ і Δ_local; |Δ|≥0.7 та |Δ_local|≥0.7; підтримка ≥2/3 і протилежні тижні ≤20%.

Нехай s=sign(Δ), за умови узгодження з Δ_local:
- підтримка: s*Δ_t ≥ 0.3;
- протилежність: s*Δ_t ≤ −0.3;
- нейтральний: |Δ_t| < 0.3.

Нейтральні тижні лишаються у знаменнику K. Перевіряти точно: 3*support≥2*K та 5*opposite≤K. Не замінювати 2/3 на 0.66; не поєднувати «≤1» і «≤20%» через довільне OR. Рівно ±0.3 належать відповідному напрямку. Кожен тиждень має один голос у повторюваності, ваги w_t стосуються лише Δ_local. Не рахувати перекривні ковзні вікна як незалежні підтвердження.

Це погоджені продуктові пороги, не p-value, не доведена статистична значущість і не ймовірність причинного впливу. Для 7/7 без групи B можливі регулярність та описовий підсумок, але неможливий контраст «з/без».

### Контекст

Окремо перевірити статус і календарний тип дня (пн–пт / сб–нд; не називати це робочими/вільними днями). Потім спільні підгрупи, коли є дані. Для аналізу статусу не контролювати сам статус; для емоцій та звичок — доступні статус і тип дня.

Використовувати підгрупи з nAs≥2,nBs≥2; Δ_s і w_s рахуються аналогічно. Вага враховує чисельність, не дисперсію. Окремі перевірки зі збереженим знаком не доводять, що спільний контекст перевірено.

Показувати число підгруп і охоплення окремо A та B. Відмовитися від загального правила «<50% — усе приховати». Частковий результат формулювати лише для включених контекстів. Зміна знаку — пояснення залежності від контексту; брак даних — невизначеність. Для рівня 3 контекстна суперечність блокує загальну позитивну інтерпретацію, але не приховує базові числа чи сам факт суперечності. Непроведена перевірка не вважається успішною.

Не перебирати всі комбінації кількох звичок/емоцій у першій версії. Численні перевірки та залежність сусідніх днів створюють випадкові закономірності; пороги не усувають це автоматично.

## 5. Етап A — точна специфікація реалізації

### A1. Читач без мутацій

Створити окремі чисті функції читання профілю дня та періоду. Входи: знімок стану, dateKey або from/to, явна дата asOf. Виходи: профіль із метриками, кількостями, ID джерел, unknown-полями та обмеженнями. Назви функцій — readInsightDay/readInsightPeriod; повертати нові об'єкти/масиви без посилань, які дозволяють змінити вихідний стан.

Не викликати day(), ensureSummaryEntries(), save(), persist(), DOM, Date.now() чи Math.random() всередині читача. ensureSummaryEntries мутує дані, генерує ID/час і перебудовує об'єкти. Не створювати записів у S.days під час перебору календаря.

Мінімальний профіль дня: dateKey; ratings {count,mean,range,meanAbsoluteDeviation,entries}; entries {count,textCount,voiceCount}; emotions {uniqueIds,knownLevels,unknownIds}; status {id,known}; habits {markedIds}; flags наявності відправлених даних, оцінок/емоцій/статусу; quality з походженням часу та діагностикою невалідних елементів. Нульовий count допустимий; відсутня числова метрика — null.

Профіль періоду: фактичний діапазон, календарна кількість минулих днів, профілі днів, counts/coverage за кожним каналом, mean/median оцінених днів, розкид, сусідні пари, підсумки записів, частоти емоцій. Подальші контрасти і відбір карток — поза A.

Валідні ID емоцій об'єднати із дня, entries та legacy-полів. Категорії built-in — чинний каталог; власні об'єкти з level строго pos/neu/neg — збережена категорія. Рядок, відсутнє чи невалідне level або ID без визначення — unknown. Не використовувати запасне neu з allEmotions() як факт. Відсутність категорії не видаляє саму емоцію.

Чернетка day.draftText та _voicePreviewBlob не беруть участі. Не підраховувати весь summary ще раз, коли є відправлені entries. Дублі емоцій усувати за ID, не за текстом коментаря. Для legacy-профілю не генерувати нових timestamps/випадкових ID; за відсутності ID використовувати стабільне внутрішнє посилання дата+індекс без збереження в журнал.

### A2. Походження нових оцінок

У момент кліку один раз захопити Date та dateKey активного дня. З цього самого Date отримати ts, t=HH:MM та recordedDay=локальний YYYY-MM-DD.

Новий об'єкт:
{v, t, ts, recordedDay, retro: dateKey !== recordedDay}

Не порівнювати з кешованим TODAY: його оновлення після опівночі може відкладатися через чернетку. recordedDay зберігає локальну дату на момент внесення, щоб подальша зміна часового поясу не переписувала походження.

Редагування існуючого об'єкта: змінити v, додати edited:true та editedAt з моменту кліку; початкові t/ts/recordedDay/retro зберегти. Редагування legacy-числа: {v,edited:true,editedAt}, без вигаданого t/ts. Для старого об'єкта без ts початкове походження лишається unknown. Відсутній retro не дорівнює false.

У профілі недійсні metadata не повинні робити валідну оцінку невалідною: значення бере участь у середньому, час — unknown із діагностикою. Нові поля мають переживати збереження, reload, JSON/ZIP export/import та merge. Перевірити всі місця перетворення оцінок; одного ratingVal недостатньо для заяви про повну сумісність. Не додавати мітки старим оцінкам заднім числом.

Зберегти чинну обробку невдалого запису: відкат стосується і нових metadata. Не змінювати схему медіа або single-writer.

### A3. Межі

Етап A додає підготовку даних і запис походження нових оцінок. Не перебудовувати поточні картки/стикери, не міняти ваги оцінок, не переносити/видаляти Insights, не робити аналіз тексту, не розвивати AI. Міграція нових полів для всіх старих summaryEntries не потрібна: читач позначає їхнє походження як невідоме. Якщо колись додається migrated-флаг, його треба явно зберігати через нормалізатор; евристика «00:00 + один запис» не є доказом міграції.

### A4. Критерії приймання

- Заморожений вхід читається без помилки мутації; серіалізований стан до/після ідентичний. Повторний виклик дає той самий результат; немає записів у storage.
- Оцінки: числа, об'єкти, legacy dayRating, порожні й невалідні елементи; день 2 і день із дев'ятьма 8 дають середню 5.0. Одна оцінка не дає нульової «стабільності».
- Пропуски та майбутнє: null замість нулів; no-rating дні входять у покриття; сусідні пари не перестрибують пропуски. Дні лише з habitLog враховуються як спостережувані.
- Емоції: повтор у записах/дні рахується один раз; власна pos/neu/neg врахована; рядкова/невалідна/невідома не стає neutral.
- Entries: summary і entries не дублюються; legacy summary підтримано; _summaryCleared дотримано; draftText/voicePreview виключені; справжній один запис 00:00 не оголошено мігрованим.
- Час: нова оцінка сьогодні/вчора; новий день при застарілому TODAY; захоплення часу біля опівночі; зміна часового поясу; редагування нового/legacy об'єкта з незмінним початковим ts; editedAt оновлюється.
- Збереження: metadata переживає reload та JSON/ZIP round-trip; помилка запису відкочує значення і metadata; старі архіви працюють. Повний імпортний аудит поза цим набором не оголошувати закритим.
- Дати: UTC−/UTC+, перехід DST, лютий високосного року, межі місяця/року; сьогодні задається явно в чистих функціях.
- Регресія UI: додавання/редагування/видалення, нейтральна шкала, перехід між днями, popup і скрол, light/dark, UK/EN. Реальний iPhone перевіряє автор.

## 6. Подальші етапи та вихід для користувача

B: описова аналітика й порівняння періодів на профілях A. C: групові/локальні контрасти, повторюваність і контекст за розділом 4. D: відбір, тексти й деталізація.

Кандидат інсайту має тип, діапазон, числа, кількості, посилання на дні, підтримку/протилежність/нейтральність та обмеження. Числа обчислюються окремо від шаблонів UK/EN. Однакові дані — однаковий результат, без випадкової варіації тексту.

До трьох карток: основна зміна/підсумок; контекстний зв'язок; емоційне спостереження або суттєва неповнота. Не заповнювати три слоти вигаданими висновками. Деталі показують дати, групи, формулу й обмеження. Суперечність контексту — окрема пояснювальна картка, не позитивний висновок про користь звички.

Перевірка B–D: звички 1–7 разів/тиждень; 7/7 без групи B; приклад 5 тижнів +1.2 і 2 тижні +0.2; від'ємний напрямок; межі ±0.3, 2/3,20%; змішування буднів/статусів із переворотом знаку; тренд у часі без зв'язку; розріджені оцінки; нерівне покриття A/B; випадкові дані з великою кількістю звичок; видалення та редагування змінюють результати. Не підганяти пороги під один зручний приклад; зміну погоджених чисел обговорити з автором.
